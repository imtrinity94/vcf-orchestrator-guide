A REST call needs the other side to be up and listening at that moment. A message queue doesn't: the workflow hands a message to a broker and carries on, and whoever reads the queue picks it up when it's ready, even hours later. That makes queues a good fit for telling other systems that something happened, such as a VM built or a request approved, and for taking work from systems that can't call Orchestrator's API themselves.

The AMQP plug-in talks to brokers that speak AMQP 0-9-1, which in practice means RabbitMQ. In this recipe you register a broker, set up an exchange and a queue with the built-in workflows, publish VM facts as JSON from an action, and read them back. **There's more** shows how a message can start a workflow.

<Recipe type="ready">

- A RabbitMQ server that Orchestrator can reach. This recipe uses `mq01.vmw.lab` on port `5672`, the virtual host `/`, and a RabbitMQ user `vcfguide` that may configure, write, and read there.
- The action `vmFactsToJson` from recipe 5.6, and the vCenter `vc01.vmw.lab`.
- A login with administrator rights and the action module `com.vcfguide.chapter5`.

</Recipe>

<Recipe type="how">

**Register the broker**

1. Go to **Library** > **Workflows**, search with the tags `amqp` and `configuration`, and run **Add a broker**.
2. On the **AMQP broker properties** tab, enter the **Name** `mq01`.
3. On the **AMQP connection properties** tab, enter the **Host** `mq01.vmw.lab`, leave **Port** at `5672` and **Virtual host** at `/`, leave **Use SSL** off, and enter the user `vcfguide` and its password. Click **Run**.
4. Run **Validate a broker** and select `mq01`. The run completes without an error. If it fails, fix the setting with **Update a broker**.
5. Go to **Administration** > **Inventory** > **AMQP**. The broker `mq01` is listed.

<Verify>On 9.1.1, check the name of the inventory entry for brokers (<b>AMQP</b> or <b>AMQP Plug-in</b>) and what <b>Validate a broker</b> reports on success and on a wrong password.</Verify>

**Declare an exchange, a queue, and a binding**

6. Search with the tag `amqp` and run **Declare an exchange**. Select `mq01`, enter the name `vcfguide.events`, choose the type **topic**, set **Durable** to **Yes**, and leave automatic deletion at **No**.
7. Run **Declare a queue**. Select `mq01`, enter the name `vcfguide.vm-facts`, set **Durable** to **Yes**, and leave **Exclusive** and **Auto-delete** at **No**.
8. Run **Bind**. Select `mq01`, and enter the queue `vcfguide.vm-facts`, the exchange `vcfguide.events`, and the routing key `vm.facts.#`.
9. In the RabbitMQ management UI, open the exchange `vcfguide.events`. Its **Bindings** list shows the queue with the key `vm.facts.#`.

**Try it without code**

10. Run **Send a text message**. Select `mq01`, enter the exchange `vcfguide.events`, the routing key `vm.facts.test`, and the text `hello from vco01`.
11. Run **Receive a text message**. Select `mq01` and enter the queue `vcfguide.vm-facts`. The run's output is `hello from vco01`, and the queue is empty again.

**Publish from an action**

12. In **Library** > **Actions**, create the action `getBroker` in `com.vcfguide.chapter5`, with the input `name` of type `string` and the **Return type** `AMQP:Broker`:

```javascript title="com.vcfguide.chapter5/getBroker"
// Returns the AMQP broker registered under this name.
var brokers = Server.findAllForType("AMQP:Broker", null);
for (var i = 0; i < brokers.length; i++) {
    if (brokers[i].name === name) {
        return brokers[i];
    }
}
throw "getBroker: no AMQP broker named " + name;
```

13. Create the action `publishVmFacts`, with the inputs `brokerName` of type `string` and `vms` of type `Array/VC:VirtualMachine`, and the **Return type** `void`:

```javascript title="com.vcfguide.chapter5/publishVmFacts"
// Publishes the facts of the VMs as one JSON message to vcfguide.events.
var chapter5 = System.getModule("com.vcfguide.chapter5");
var broker = chapter5.getBroker(brokerName);

var message = new AMQPMessage();
message.bodyAsText = chapter5.vmFactsToJson(vms);

var headers = new Properties();
headers.put("content_type", "application/json");
headers.put("source", "vco01.vmw.lab");
message.headers = headers;

broker.send("vcfguide.events", "vm.facts.report", message);
System.log("Published facts of " + vms.length + " VMs to vcfguide.events on " + brokerName);
```

14. Run `publishVmFacts` with `mq01` and two VMs. In the RabbitMQ management UI, the queue `vcfguide.vm-facts` now holds one message.

**Read from an action**

15. Create the action `receiveVmFacts`, with the input `brokerName` of type `string` and the **Return type** `Array/Properties`:

```javascript title="com.vcfguide.chapter5/receiveVmFacts"
// Takes one message from vcfguide.vm-facts and returns the VMs in it,
// or an empty array if the queue is empty.
var chapter5 = System.getModule("com.vcfguide.chapter5");
var broker = chapter5.getBroker(brokerName);

var message = broker.receive("vcfguide.vm-facts");
if (!message) {
    System.log("No message waiting in vcfguide.vm-facts");
    return [];
}
return chapter5.parseVmFactsJson(message.bodyAsText);
```

16. Run it with `mq01`. The result is the two VMs from step 14. Run it again: the log says *No message waiting*.

<Recipe type="works">

**Exchanges, queues, and bindings.** In AMQP 0-9-1, a sender never writes to a queue. It sends a message to an **exchange** with a **routing key**, and the exchange copies it into every queue whose **binding** matches the key. A **topic** exchange matches keys made of words separated by dots: `*` stands for one word and `#` for any number of words, so `vm.facts.#` catches `vm.facts.report` and `vm.facts.test`. Other systems can bind their own queues to `vcfguide.events` with other keys, and each gets its own copy, without any change to the workflow.

**Durable.** A durable exchange or queue survives a restart of the broker. Messages survive too only if they're sent as persistent; check the delivery mode your broker and readers expect before you rely on it.

**The broker object.** **Add a broker** stores the connection in Orchestrator and makes the broker an inventory object, so scripts find it by name with `Server.findAllForType` and never see the password. The broker object can also declare exchanges and queues itself, with `declareExchange`, `declareQueue`, and `bind`, which is how a workflow can set up what it needs on a fresh broker.

**Receive takes one message.** `receive(queue)` takes the next message off the queue, or nothing if it's empty, and returns at once. It's for a workflow that checks a queue now and then. To react to each message as it arrives, use a subscription, below.

<Recipe type="more">

**Start a workflow when a message arrives.** Run **Subscribe to queues** (tags `amqp` and `configuration`), enter the name `vcfguide-vm-facts`, select `mq01`, and select the queue `vcfguide.vm-facts`. The subscription appears under the broker in the inventory. Then create a workflow, **Handle VM facts message**, with one input, `subscription` of type `AMQP:Subscription`, and a scriptable task:

```javascript title="Handle VM facts message / Read message"
// Called by the policy for each message on the subscription's queues.
var trigger = subscription.retrieveLastOnMessageTrigger();
var message = subscription.retrieveMessage(trigger);
var vms = System.getModule("com.vcfguide.chapter5").parseVmFactsJson(message.bodyAsText);
System.log("Message with " + vms.length + " VMs received on " + subscription.name);
```

Go to **Library** > **Policies** and create the policy **VCF Guide VM facts**. On the **Definition** tab, add a policy element for the subscription `vcfguide-vm-facts`, add its **OnMessage** event, and point the event at **Handle VM facts message**, with the policy element bound to `subscription`. Run the policy. Each message now starts a run of the workflow, which you'll find under **Activity** > **Policy Runs**.

<Verify>Build this policy on 9.1.1 and record every step: the policy element type for a subscription, the exact name and casing of the message event (<b>OnMessage</b> or <b>onMessage</b>), how the element is passed to the workflow's input, and the scripting type <code>AMQP:Subscription</code>. Check that <code>retrieveLastOnMessageTrigger</code> and <code>retrieveMessage</code> work as shown, and which user the policy's runs use in 9.x (KB 446432).</Verify>

**TLS.** Set **Use SSL** to **Yes** and use RabbitMQ's TLS port, usually `5671`. Import the broker's certificate first with **Import a certificate from URL**, rather than choosing **Accept all certificates**, which turns off the check. If RabbitMQ allows only TLS 1.3, connections fail with *protocol_version* until you run `vracli vro properties set -k o11n.plugin.amqp.ssl-context-protocol -v TLSv1.3` on the appliance (KB 427111, recipe 2.8).

<Verify>Confirm that <b>Import a certificate from URL</b> can read the certificate of <code>mq01.vmw.lab:5671</code>, and that a broker with <b>Use SSL</b> and without <b>Accept all certificates</b> connects once it's imported.</Verify>

**Request and reply.** `broker.sendAndReceive(exchange, routingKey, message, timeoutSeconds)` sends a message and waits for the answer, for systems that reply on a queue. Keep the timeout short: the workflow run holds a thread while it waits.

**Kafka and other brokers.** Orchestrator 9.x has no Kafka plug-in, and the AMQP plug-in speaks only AMQP 0-9-1, not AMQP 1.0. For Kafka, call a Kafka REST proxy with the HTTP-REST plug-in (recipe 5.2), or use a Kafka client library from a Node.js or Python action (Chapter 4).

</Recipe>
