Chapter 3 drew workflows. This chapter is about the code inside them. Every scriptable task, action, custom decision, and form action is a script, and the quality of those scripts decides whether a workflow is easy to trust and change, or a puzzle for whoever opens it next.

Recipe 4.1 starts with the engine that runs your JavaScript, and why this book keeps to plain ES5.1. Recipe 4.2 turns scripts into a library of small actions that other workflows call, and shows how to change them without breaking anything. Recipe 4.3 steps outside JavaScript to Python, and to the environments that give a script its packages. Recipes 4.4 and 4.5 do the same for Node.js, with its callbacks, and for PowerShell and PowerCLI, with their habit of returning more than you meant. The last two recipes are about habits that apply in every language: recipe 4.6 makes scripts leave a useful log behind, and recipe 4.7 moves settings and credentials out of code and into configuration elements.

## The examples

Most examples in this chapter are actions, so they go in one module:

| Object | Name |
|---|---|
| Action module | `com.vcfguide.chapter4` |
| Workflow folder, for anything that needs one | **VCF Orchestrator Guide/Chapter 4** |
| Environments | `vcfguide-python-crypto`, `vcfguide-node-semver` |
| Configuration elements, in the folder **VCF Orchestrator Guide/Chapter 4** | `vcfguide-settings`, and `vc01.vmw.lab` in the subfolder **vCenters** |

Like Chapter 3, the examples only read from the lab: the vCenter `vc01.vmw.lab`, its VMs and snapshots, and the TLS certificate it presents. The PowerCLI examples connect to it with a read-only account, `svc-vcfguide-ro@vsphere.local`. JavaScript samples, including those for the Node.js runtime, are plain ES5.1. Python samples are ordinary Python 3.10, and PowerShell samples run in PowerShell 7.4.
