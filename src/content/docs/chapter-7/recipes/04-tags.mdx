A busy Orchestrator holds thousands of workflows and actions, most of them from plug-ins. Folders sort them one way. **Tags** sort them any other way you like: by team, by purpose, by the system they touch, by whether they're safe to run in production. A tag is a short label, and one object can carry many.

Orchestrator has two kinds of tag that are easy to confuse. The first kind is the tags you set on your own workflows in the client, so that the library search can find them. The second kind is tags you set from scripts on any object Orchestrator knows about, including plug-in objects such as a vCenter VM, so that a later workflow can ask "which objects carry this tag?". This recipe does both. Neither kind is a vSphere tag: Orchestrator keeps its tags in its own database, and vCenter never sees them.

**Tag your own workflows**

1. Go to **Library** > **Workflows** and open **Count powered-on VMs** from recipe 7.3.
2. On the **General** tab, find the **Tags** field. Type `vcfguide` and press **Enter**, then add `read-only` and `vcenter` in the same way. Click **Save**.
3. Open **List VMs by name** and give it the same three tags. Save it.

**Tag plug-in objects from a script**

5. Under **Library** > **Actions**, in the module `com.vcfguide.chapter7`, create the action `tagVm`. Give it three inputs, `vm` (`VC:VirtualMachine`), `tagName` (`string`) and `tagValue` (`string`), and the return type `void`.
6. Enter the script and save:

```javascript title="com.vcfguide.chapter7/tagVm"
// Private tag: visible only to the user this action runs as.
if (tagName.length < 3 || tagName.length > 64 || /\s/.test(tagName)) {
    throw "Tag names are 3 to 64 characters with no spaces: " + tagName;
}
Server.tag(vm, tagName, tagValue);
System.log("Tagged " + vm.name + " with " + tagName + " = " + tagValue);
```

7. Create a second action, `findVmsByTag`, with one input, `tagName` (`string`), and the return type `Array/VC:VirtualMachine`:

```javascript title="com.vcfguide.chapter7/findVmsByTag"
var query = [{ tag: tagName }];
var found = Server.queryByTags(query, "VC:VirtualMachine");
var result = [];
for (var i = 0; i < found.length; i++) {
    result.push(found[i]);
}
System.log(result.length + " VMs carry the tag " + tagName);
return result;
```

8. Run `tagVm` on one VM in `vc01.vmw.lab` with `tagName` = `vcfguide-owner` and `tagValue` = `platform-team`. Then run `findVmsByTag` with `tagName` = `vcfguide-owner`. It returns that one VM.

**Make a tag everyone can see**

9. A private tag is only visible to the user who set it. A tag that other users and other workflows should rely on must be **global**. Copy `tagVm` to a new action, `tagVmGlobally`, and change the `Server.tag` line to:

```javascript title="com.vcfguide.chapter7/tagVmGlobally — the changed line"
Server.tagGlobally(vm, tagName, tagValue);
```

10. Run `tagVmGlobally` as an administrator on two VMs, with `tagName` = `vcfguide-backup` and `tagValue` = `daily`.
11. Log in as a different user, one who isn't the administrator from step 8 but can run actions, and run `findVmsByTag` with `tagName` = `vcfguide-backup`. It returns both VMs. Run it with `vcfguide-owner`. It returns nothing, because that tag was private to the administrator who set it.

<Recipe type="works">

**Two tag stores.** The tags you type on a workflow's **General** tab are part of the workflow. They're saved in its definition, travel with it in packages and Git (Chapter 6), and show up in version history. They exist to make the library searchable. Standard workflows that ship with Orchestrator carry their own tags, which is why searching for `SSH` finds the SSH workflows. You can't add tags to a standard workflow, because it's read-only. Duplicate it first.

The tags you set with `Server.tag` and `Server.tagGlobally` live elsewhere: in a table in the Orchestrator database that links an object's type and ID to a tag name, an optional value, and an owner. The object itself isn't changed. That's why they work on plug-in objects, such as a `VC:VirtualMachine`, that Orchestrator doesn't own and can't modify.

**Private and global.** Every scripted tag has an owner. A **private** tag belongs to the user who ran the script and is visible only to that user. A **global** tag is visible to everyone, and only administrators can create or remove one. Use private tags for a user's own bookmarks, and global tags for anything another workflow depends on.

| | Workflow tags | Private tags | Global tags |
|---|---|---|---|
| Set with | **General** tab, **Tags** field | `Server.tag` | `Server.tagGlobally` |
| On | Your workflows | Any object Orchestrator can reference | Any object Orchestrator can reference |
| Seen by | Everyone who can see the workflow | The owner only | Everyone |
| Travels in packages | Yes | No | No |

**Names and values.** A tag name is 3 to 64 characters, with no spaces. The value is optional free text. Keep names in a namespace, like `vcfguide-backup`, so your tags don't collide with someone else's `backup`.

**What a tag query costs.** `Server.queryByTags` asks the Orchestrator database, not the plug-in. It's quick, and it doesn't touch vCenter until you read a property of a returned object. That makes tags a cheap index: "which VMs did our provisioning workflow build?" is one query, instead of a loop over every VM in the inventory.

**Tags point at IDs.** A scripted tag remembers the object's ID. If the object goes away, for example a VM is deleted, the tag stays behind, pointing at nothing. A query may return objects that no longer resolve.

<Recipe type="more">

**Tags or vSphere tags?** If the label needs to be seen in the vSphere Client, used by a storage policy, or read by another tool, it must be a vSphere tag, set in vCenter through the vAPI plug-in. Use Orchestrator tags for labels that only Orchestrator content needs. Chapter 8's recipes on vCenter workflows cover vSphere tags.

**Removing tags.** `Server.untag(object, tagName)` and `Server.untagGlobally(object, tagName)` take a tag off an object. Remove the tags a workflow set when it removes the object, for example in the same workflow that deletes a VM, so that queries don't return stale IDs.

<Verify>Confirm the names and parameters of <code>Server.untag</code> and <code>Server.untagGlobally</code> in the 9.1.1 API Explorer.</Verify>

**Tags as a work list.** A scheduled workflow (recipe 7.7) can run `findVmsByTag("vcfguide-backup")` each night and act on whatever it returns. Adding a VM to the job means tagging it, not editing the workflow.

**Tag conventions.** Agree on a short list of global tag names for your team and write them down, next to the naming conventions from this book's introduction. A tag nobody else uses is a private bookmark, however global it is.

</Recipe>
