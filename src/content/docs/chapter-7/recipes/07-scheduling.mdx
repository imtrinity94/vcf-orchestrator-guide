Some work needs doing at a set time: a report every morning, a clean-up every Sunday night, a change in tonight's maintenance window. Recipe 7.3 used a policy for work at intervals. For most timetable jobs a **schedule** is simpler. It's one workflow, one set of inputs, and a recurrence, and Orchestrator starts the run when the time comes.

In this recipe you schedule **Build VM report** from recipe 7.6 to run every weekday morning, look at what decides whose identity the run uses, and then do the same from a script and from the REST API. The last part is about the thing that makes schedules fail quietly: the stored credentials of the starting user.

<Recipe type="how">

**Schedule a recurring run**

1. Go to **Library** > **Workflows** and open **Build VM report**, or select its card. Click **Schedule**.
2. Under **General**, enter the name `VM report every weekday` and the description `Builds the Chapter 7 VM report at 06:00, Monday to Friday.`
3. Set **Starting user**. Leave it at the current user for now. **How it works** explains the three choices.
4. Under **Scheduling**, set **Start** to tomorrow at `06:00`, and **Start if in the past** to **No**, so that a schedule saved after 06:00 waits for the next morning instead of running at once.
5. In **Schedule**, add a recurrence that repeats every day at `06:00`, limited to Monday to Friday.
6. **Build VM report** has no inputs, so there's no **Workflow** section. For a workflow with inputs, that section asks for the values the scheduled runs will use, as a run would.
7. Click **Save**.

**Schedule a one-off run from a script**

12. Some runs should happen once, at a set time: a change at 22:00 tonight, or a clean-up the day after a VM is built. Create the action `com.vcfguide.chapter7/scheduleReportAt` with one input, `startAt` (`Date`), and the return type `Task`:

```javascript title="com.vcfguide.chapter7/scheduleReportAt"
var wf = null;
var found = Server.getWorkflowsWithName("Build VM report");
for (var i = 0; i < found.length; i++) {
    if (found[i].workflowCategory.path === "VCF Orchestrator Guide/Chapter 7") {
        wf = found[i];
    }
}
if (!wf) {
    throw "Workflow Build VM report not found in VCF Orchestrator Guide/Chapter 7";
}

var props = new Properties();
// Inputs of the workflow go here, by name. Build VM report has none.
props.put("__taskName", "VM report once at " + startAt.toString());
props.put("__taskDescription", "One-off run scheduled by scheduleReportAt");

var task = wf.schedule(props, startAt);
System.log("Scheduled " + task.name + " for " + startAt);
return task;
```

13. Run it with `startAt` set to ten minutes from now. The schedule appears in **Activity** > **Scheduled** with the name from `__taskName`. Ten minutes later it runs once and doesn't run again.

**Manage schedules through the REST API**

14. List the schedules on the server:

```bash
. vro-env.sh
vro GET '/tasks' | jq '.link[] | [(.attributes[] | select(.name=="name") | .value), .href]'
```

15. A pipeline that deploys a new version of the report workflow can remove the old schedule and create a new one. Delete a schedule by its ID:

```bash
TASK_ID="<ID from the href>"
vro DELETE "/tasks/$TASK_ID"
```

<Recipe type="works">

**A schedule is a task.** In the API and in scripts, a schedule is a `Task`: a workflow, a set of input values, a start time, a recurrence, and a starting user. Orchestrator's scheduler checks its tasks and starts a normal workflow run when one is due. The run is like any other: it shows in **Activity** > **Workflow Runs**, it has a log and variables, and it counts against the server's limit of concurrent runs.

**Start if in the past.** A schedule's start time can be in the past when you save it, or pass while the server is down. **Yes** runs the workflow at once in that case. **No** waits for the next time in the recurrence. Choose **No** for reports, so that a server restart at 09:00 doesn't send the morning report twice. Choose **Yes** for work that must happen once, such as a change that was due during the outage.

**Whose identity the run uses.** A scheduled run happens when nobody is logged in, so Orchestrator keeps a way to authenticate as the **Starting user**:

| Starting user | The run authenticates as | Watch out for |
|---|---|---|
| The current user | You, with credentials Orchestrator stored when you saved | Your account changing: a new password, leaving the team, a disabled account |
| The Orchestrator system user | Orchestrator's own service identity | Runs that aren't traceable to a person, and rights that may differ from yours |
| An API token | The account that owns the token | The token expiring or being revoked |

Pick the one that will still be valid in a year. For production jobs, an API token that belongs to a service account, such as `svc-vcfguide@vsphere.local` on a standalone appliance or a service account in VCF Automation, survives people changing jobs.

**When schedules stop.** A schedule whose credentials stop working doesn't fail loudly. It just stops starting runs, or its runs fail at the first step. Broadcom's 9.0 known issues list two cases. On a standalone Orchestrator that uses VCF SSO authentication, scheduled workflows stopped running some 30 to 60 minutes after the user who scheduled them stopped using the client. On the Orchestrator embedded in VCF Automation, scheduling with the service account or an API token failed with *Can not login in VMware Cloud Foundation Automation with username and password*. Broadcom KB 445644 has a workaround for the embedded case and says it's fixed in VCF Automation 9.1.1, after which an API token for scheduling takes the form `{apiToken}@orgName:{tenantName}`.

<Recipe type="more">

**Schedule or policy?** Use a schedule for "run this workflow at these times". Use a policy (recipe 7.3) when you need several handlers that share variables, start and stop hooks, or events from a plug-in. A schedule has nothing to keep running, so there's less to go wrong after a restart.

**Inputs that change.** A schedule stores its input values when you save it. If a value should be worked out at run time, such as yesterday's date, don't pass it as an input. Let the workflow calculate it, or read it from a configuration element (recipe 4.7).

**Don't let runs pile up.** If a run takes longer than the interval, the next one starts anyway, and two runs work on the same thing. Choose an interval longer than the workflow takes, or protect the work with a lock (recipe 7.5) and make the second run give up instead of waiting.

**Tags as the job list.** Combine this recipe with recipe 7.4: a nightly schedule runs a workflow that calls `findVmsByTag("vcfguide-backup")` and acts on each VM it returns. Adding a VM to the job is a tag, not a change to the schedule.

**Watch your schedules.** Because a broken schedule fails quietly, check **Activity** > **Scheduled** after an upgrade, a certificate change, or a change to the authentication provider. A small daily workflow that compares each schedule's last run with its recurrence, through the **Task Service**, catches the ones that stopped.

</Recipe>
