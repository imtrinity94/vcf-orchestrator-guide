Chapters 3 to 5 built workflows, actions, and configuration elements, and every one of them lived on a single Orchestrator. Sooner or later that content has to go somewhere else: to a second instance where it can be tested, to production, or to a colleague. And sooner or later someone saves a change they wish they hadn't. This chapter is about both: knowing what changed, getting back to a version that worked, and moving content between instances without losing anything on the way.

Recipe 6.1 starts on one server, with the version history Orchestrator keeps for every object, and the place deleted objects go. Recipe 6.2 bundles a workflow with the actions and configuration elements it needs into a **package**, exports it, and imports it into a second Orchestrator. Recipe 6.3 connects Orchestrator to a Git repository, so every change is pushed to a server your team already backs up and reviews. Recipe 6.4 puts the two together into a route from development to production, once with packages through the REST API and once with Git branches and a pull request.

## The examples

All four recipes use one small set of content, built in recipe 6.1, so you can see the same objects move from version history to a package to Git:

| Object | Name |
|---|---|
| Workflow, in **VCF Orchestrator Guide/Chapter 6** | **Report powered-on VMs** |
| Action module | `com.vcfguide.chapter6`, with the action `countPoweredOnVms` |
| Configuration element, in **VCF Orchestrator Guide/Chapter 6** | `vcfguide-ch6-settings`, with `reportPrefix` (`string`) and `apiToken` (`SecureString`) |
| Package | `com.vcfguide.chapter6` |
| Development Orchestrator | `vco01.vmw.lab`, the standalone appliance |
| Production Orchestrator, for the lab | the Orchestrator embedded in VCF Automation, `auto.vmw.lab` |
| Git repository | a private GitHub repository, `vcfguide-content`, with the branches `develop` and `main` |

The lab has only one standalone appliance, so the embedded Orchestrator in VCF Automation stands in for production. In a real environment both ends would usually be standalone appliances, or clusters. Nothing in the recipes depends on which kind is which. The workflow only reads from `vc01.vmw.lab`, so it's safe to run on both. JavaScript samples are plain ES5.1.

## What changed since vRO 7

The idea of a package hasn't changed in fifteen years, and a `.package` file from an old server still looks familiar inside. Around it, almost everything is new.

<ThenNow
  then="A version history entry was kept only when you raised a workflow's version number and saved. Unversioned edits were lost on revert."
