Before content leaves a server, it has a history on that server. Orchestrator keeps a record of every saved version of a workflow, action, policy, configuration element, resource element, and package. You can see what changed between two saves, and go back to any of them. Deleting an object doesn't throw that history away either: deleted objects wait under **Deleted Items** until you restore them.

In this recipe you build the small set of content the rest of the chapter uses, change it once, compare the two versions, restore the first one, and then delete the workflow and bring it back.

<Recipe type="ready">

- A login to the Orchestrator Client on `vco01.vmw.lab` with a role that can create workflows, actions, and configuration elements.
- The vCenter `vc01.vmw.lab` registered with the vSphere plug-in, as in recipe 1.9.
- The folders **VCF Orchestrator Guide/Chapter 6** under both **Library** > **Workflows** and **Assets** > **Configurations**.

</Recipe>

<Recipe type="how">

**Build the example content**

1. Go to **Assets** > **Configurations**, open the folder **VCF Orchestrator Guide/Chapter 6**, and click **New Configuration**. Name it `vcfguide-ch6-settings`.
2. On the **Variables** tab, add two variables and click **Save**:

| Name | Type | Value |
|---|---|---|
| `reportPrefix` | `string` | `VCF Guide` |
| `apiToken` | `SecureString` | `not-a-real-secret` |

The workflow only reads `reportPrefix`. `apiToken` stands in for the credential a real workflow would keep here, so you can see what happens to secrets in recipes 6.2 and 6.3.

3. Go to **Library** > **Workflows**, open the folder **VCF Orchestrator Guide/Chapter 6**, and create the workflow **Report powered-on VMs**. On the **General** tab, set the **Version** to `1.0.0`.
4. On the **Variables** tab, add a variable `reportPrefix` of type `string` and bind it to the configuration element `vcfguide-ch6-settings`, variable `reportPrefix`, as in recipe 4.7.
5. On the **Schema** tab, add a scriptable task named **Count VMs**, give it `reportPrefix` as an input, and enter:

```javascript title="Report powered-on VMs / Count VMs — version 1.0.0"
// reportPrefix comes from the configuration element vcfguide-ch6-settings
var vms = VcPlugin.getAllVirtualMachines();
System.log(reportPrefix + ": " + vms.length + " VMs in the vSphere inventory");
```

6. Click **Save**, then **Run**. The log shows one line, such as *VCF Guide: 57 VMs in the vSphere inventory*.

**Change it**

7. In **Library** > **Actions**, create the action `countPoweredOnVms` in a new module, `com.vcfguide.chapter6`. It has no inputs and the **Return type** `number`:

```javascript title="com.vcfguide.chapter6/countPoweredOnVms"
// Returns the number of powered-on VMs across every registered vCenter.
var vms = VcPlugin.getAllVirtualMachines();
var count = 0;
for (var i = 0; i < vms.length; i++) {
    if (vms[i].runtime.powerState.value === "poweredOn") {
        count++;
    }
}
return count;
```

8. Open **Report powered-on VMs** again. Replace the script of **Count VMs** with:

```javascript title="Report powered-on VMs / Count VMs — version 1.1.0"
// reportPrefix comes from the configuration element vcfguide-ch6-settings
var chapter6 = System.getModule("com.vcfguide.chapter6");
var total = VcPlugin.getAllVirtualMachines().length;
var poweredOn = chapter6.countPoweredOnVms();
System.log(reportPrefix + ": " + poweredOn + " of " + total + " VMs powered on");
```

9. On the **General** tab, change the **Version** to `1.1.0`, add `Counts powered-on VMs with an action` to the description, and click **Save**. Run it again: the log now says *VCF Guide: 42 of 57 VMs powered on*.

**Compare the versions**

10. Open the **Version History** tab. There's one entry for each save, newest first, with its version number, the user who saved it, and the time.
11. Select the entry for `1.0.0`, and in the **Diff against** drop-down choose the current version. A window shows the two versions as text, with the changed script lines and the new version number and description highlighted.

**Restore an older version**

13. Back on the **Version History** tab, select `1.0.0` and click **Restore**. The workflow's script and its version number go back to `1.0.0`.
14. Look at the list again. The restore didn't remove `1.1.0`: it added a new entry at the top. Select `1.1.0` and click **Restore** to get the newer script back.

<Verify>Confirm on 9.1.1 that a restore asks for confirmation, that it adds a new entry rather than removing later ones, and which version number the restored workflow shows. Check whether unsaved edits in the open editor are lost when you restore.</Verify>

**Delete and bring back a workflow**

15. In **Library** > **Workflows**, select **Report powered-on VMs** and delete it. It disappears from the folder.
16. Go to **Deleted Items**. The workflow is listed with the time it was deleted. Select it and restore it. It goes back to **VCF Orchestrator Guide/Chapter 6** with its version history intact.

<Recipe type="works">

**Every save is a version.** Each time you save an object, Orchestrator records the whole object as it was, with the user and the time, and keeps every earlier record. Comparing two entries shows the difference between two complete objects, not a list of edits. Restoring an entry saves that old object again as the newest version, so a restore never destroys anything: you can always restore your way forward again, as in step 14.

The objects with a history are the ones you write yourself: workflows, actions, policies, configuration elements, resource elements, and packages. Plug-in inventory objects, such as a registered vCenter or a REST host, aren't on that list. They're configuration of a plug-in, not content, and you recreate them with the plug-in's configuration workflows.

**The version number is yours.** The **Version** field doesn't decide whether a history entry is made. Every save makes one. The number is for people, and for package imports: when you import a package, Orchestrator compares each element's version number with the one already on the server, and only selects elements that are newer (recipe 6.2). Raise the number whenever you change something another server should pick up.

**History is stored like Git.** Under the client, Orchestrator keeps its content in an internal Git repository on the server. Each save is a commit, the **Version History** tab is that object's log, and **Administration** > **Git History** shows the commits for the whole server. That's why the same history can be pushed to an external Git server in recipe 6.3, and why Broadcom's articles on Git problems talk about Orchestrator's "local repository". It also explains the limits: history lives in Orchestrator's database, so it's as safe as your backup of the appliance (recipe 2.6), and only as long-lived as the server.

<Verify>The description of the internal repository is drawn from Broadcom KB 314887 and KB 446735, which refer to Orchestrator's internal local Git repository and to Git-backed content storage. Confirm on 9.1.1 that <b>Administration</b> > <b>Git History</b> is present and lists local commits even when no external repository is connected.</Verify>

**Deleting marks, it doesn't erase.** A deleted workflow is marked as deleted and moved out of sight, and its version history is kept. Restoring it clears the mark, so it comes back with every earlier version.

<Recipe type="more">

**Two people, one workflow.** If someone else saves a workflow while you have it open, your save hits a **merge conflict**. Click **Resolve** next to the error. The **Resolve Conflicts** window offers **Use theirs** to keep the other person's version, **Use ours** to keep yours, or **Resolve** to edit the merged version by hand. **Resolve** is unavailable when the merged version isn't valid. The safer habit is to agree who owns which workflows.

<Verify>Reproduce a merge conflict on 9.1.1 with two users editing <b>Report powered-on VMs</b> at once, and record the error text and the three choices in <b>Resolve Conflicts</b>.</Verify>

**Actions and configuration elements work the same way.** Recipe 4.2 compared and restored versions of an action. A configuration element's history records its variables and their values, so restoring one also restores old values. For a `SecureString`, the history shows only that a value is set, never the secret.

<Verify>On 9.1.1, change <code>reportPrefix</code> in <code>vcfguide-ch6-settings</code>, save, and check what the element's <b>Version History</b> shows for <code>reportPrefix</code> and for <code>apiToken</code>, and whether restoring an older version restores the old <code>SecureString</code> value.</Verify>

**Workflows that have no history.** Workflows created by the SQL plug-in's **Generate CRUD workflows for a table** workflow (recipe 5.4) don't appear in version history and can't be pushed to Git. Duplicate a generated workflow and use the copy if you want it tracked.

**Version history from the REST API.** The 9.1 API lists a workflow's versions with `GET /vco/api/workflows/{id}/versions`, so a report or a pipeline can see who changed what without opening the client.

<Verify>Call <code>GET /vco/api/workflows/&#123;id&#125;/versions</code> for <b>Report powered-on VMs</b> on 9.1.1 (seen in a comparison of the 9.x API definitions, not in the reference pages) and record the fields of each entry.</Verify>

**Folders have no history.** A folder that still has content can only be deleted with **Force delete**, which deletes everything inside it as well. If a folder vanished with its content, look for the workflows in **Deleted Items**.

<Verify>Force-delete a test folder with one workflow in it on 9.1.1, and check that the workflow appears in <b>Deleted Items</b> and can be restored without the folder.</Verify>
