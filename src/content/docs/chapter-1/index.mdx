Orchestrator is a workflow engine. You draw a process as a schema of steps, decisions, and loops. Each step is either a small piece of script or another workflow. Orchestrator then runs that process against real systems such as vCenter, NSX, a REST API, an SSH host, or a database, through **plug-ins**. Every step is saved to its database as it runs, so a long process survives a restart and can wait for days for a human to approve something.

This chapter gets you from nothing to a working Orchestrator you can log in to, with a vCenter registered and ready for the recipes in later chapters.

## One product, many names

If you search the web for help, you'll find Orchestrator under at least five names. They're all the same product, and most of what you read about workflows, actions, and plug-ins still applies.

<NameTrail />

You'll still see the old names inside the product. The REST API lives under `/vco/api`, the Kubernetes pods are called `vco-app`, and the command-line tool is `vracli`. In this book we just say **Orchestrator**.

## Where Orchestrator lives in VCF 9

In VCF 9 you meet Orchestrator in one of two forms:

| | Embedded in VCF Automation | Standalone appliance |
|---|---|---|
| **What it is** | An Orchestrator instance that comes preinstalled and preconfigured inside VCF Automation | A separate virtual appliance you deploy from an OVA |
| **Where you open it** | The **Orchestrate** tab of the Provider Consumption organization portal, or the **Orchestrator** tab in a VM Apps organization that has it added as an integration | Its own address, `https://<orchestrator-fqdn>`, or from inside a VCF Automation organization it's integrated with |
| **Who it's for** | Provider administrators, and VM Apps organizations that share it | vSphere-only shops, VCF Operations integration, All Apps organizations, and any busy environment |
| **Authentication** | Handled by VCF Automation | You choose: vSphere, a VCF Automation organization, or VCF SSO |
| **Recipe** | [1.1](recipes/01-embedded-orchestrator/) | [1.2](recipes/02-deploying-the-appliance/) to [1.6](recipes/06-vcf-sso-authentication/) |

Broadcom recommends using the embedded instance mainly for the Provider Consumption organization, and integrating VM Apps and All Apps organizations with standalone instances. The embedded instance isn't supported for All Apps organizations at all.

## What changed since vRO 7

If you learned Orchestrator in the vCO or vRO 7 days, most of the ideas you know still hold. The way you install, configure, and log in to it has changed completely.

  then="Install on Windows, enable the copy bundled with vCenter, or deploy a SUSE-based appliance."

  then="Configure everything in the Orchestrator Configuration web page on port 8283, later called Control Center."

<ThenNow
  then="Log in through LDAP, Active Directory, or vCenter Single Sign-On."

## What we used for this chapter

The recipes were written against **VCF 9.1** with Orchestrator **9.1.1** (build 25643527). The lab domain is `vmw.lab`. The names below are used throughout, so substitute your own:

| Example name | What it is |
|---|---|
| `auto.vmw.lab` | VCF Automation, with its embedded Orchestrator |
| `vco01.vmw.lab` | A standalone Orchestrator appliance |
| `vc01.vmw.lab` | A vCenter instance |

Upgrades to 9.x are supported only from Aria Automation Orchestrator **8.18.1**. If you run something older, upgrade to 8.18.1 first. Upgrading isn't covered in this chapter.
